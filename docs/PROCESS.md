# Как работает шлюз

> Last reviewed: 2026-08-13

Как работает продукт от установки до боевого трафика, плюс разбор принятых решений.

## 1. Замысел

Внутрь — обычный HTTP от приложения, наружу — BTLS (СТБ 34.101.65) с сертификатами
ГосСУОК. Приложению не нужно знать о белорусской криптографии: оно ходит по HTTP на
локальный адрес, а шлюз держит на себе TLS-терминацию, ключи и цепочки доверия.

## 2. Окружение: AvTunProxy и хосты по СТБ 34.101.65

⚠ **Раздел — кабинетный разбор по доменам, вживую не проверялся.** Прежде чем строить
на нём решение, факты подтверждаются запуском (см. правило «живые проверки — вживую»
в `CLAUDE.md`).

### 2.1. Что такое AvTunProxy

[AvTunProxy](https://avtunproxy.by/) — продукт ЗАО «АВЕСТ», локальный HTTP-прокси,
который шифрует HTTPS-трафик по **СТБ 34.101.65** и позволяет вырабатывать ЭЦП по
**СТБ 34.101.45**, используя сертификаты ГосСУОК для авторизации и подписи в разных ОС
и браузерах.

Это решение той же задачи, что и наш шлюз, но **с другого конца**:

| | AvTunProxy | bee2-tls-gateway |
| --- | --- | --- |
| Где стоит | на рабочей станции пользователя | на сервере, рядом с приложением |
| Кого обслуживает | человека в браузере | серверный процесс |
| Масштабирование | установка на каждую машину | одна точка на контур |
| Ключ | токен/контейнер у пользователя | ключ на сервере |

Отсюда и разграничение: AvTunProxy закрывает интерактивный сценарий («сотрудник зашёл
на портал и подписал»), наш случай — серверный («приложение ходит в API по расписанию»).
Конкурируют они только там, где серверную интеграцию пытаются собрать на клиентском
прокси — обычно потому, что другого инструмента под рукой не было.

### 2.2. Главный практический факт

**Ни один хост из перечня СТБ 34.101.65 не берётся обычным `curl` / Guzzle / `fetch`.**
Это архитектурный барьер, а не вопрос наличия API. Нужен либо AvTunProxy как локальный
прокси, либо серверные компоненты АВЕСТ (AvTerminal / AvCSP), либо облачная ЭЦП — либо
собственный BTLS-стек, ради которого и существует этот проект.

⚠ Цена незнания: отладка «почему не коннектится» на хосте, который по обычному TLS
не отвечает в принципе. Ошибка выглядит как сетевая, а является криптографической.

### 2.3. Кто стоит за хостами

**ЗАО «АВЕСТ» — вендор криптографии** (`*.avest.by`, `avtunproxy.by`, `eid.by`).
Семантика поддоменов повторяется во всех контурах: `oauth` / `oauthadmin` — сервер
авторизации и его админка, `legal` — авторизация юрлиц, `avterminal` — серверная
выработка и проверка ЭЦП, `app` — веб-приложение (в том числе тестовый магазин),
`cloud-ds` / `cloudsign*` — облачная подпись (в beta-контуре разложена на `api`, `pki`,
`registry`, `clients`, `storage`), `filestorage`, `tlsintotls` / `avtunproxytunnel` — сам
туннель. Префиксы `msiqa-` / `msidev-` — окружения МСИ. Для разработчиков АВЕСТ держит
тестовый магазин, сервер авторизации и тестовую площадку МСИ — это `*.dev.avest.by`
и `*.test.avest.by`.

**НКФО «ЕРИП» / МСИ** (`*.raschet.by`) — межбанковская система идентификации. `i*` —
боевой контур, `t*` / `tb*` / `tp*` — тестовые. Личный кабинет МСИ — `ioauth.raschet.by/client/`.

**НЦЭУ** (`*.nces.by`) — ГосСУОК: `uas` — боевой, `testusd2` — тестовый УЦ.

**Госорганы и ведомственные системы:**

- `nalog.gov.by` — портал МНС, личный кабинет плательщика;
- `nbrb.by` — `rvd` — веб-портал регистрации валютных договоров, `asoi` — банковская
  отчётность;
- `ssf.gov.by` + `novacom.by` — портал ФСЗН (Новаком — подрядчик);
- `e-respondent.belstat.gov.by` — электронная отчётность Белстата;
- `belpost.by` — `mail.npas` — заказные электронные почтовые отправления, `sko` / `sks` —
  ведомственные.

**СККО и программные кассы:** `skko.by`, `webkassa.by`, `ikassa.by`, `cashbox.by`,
`rdigital.by`. `iscb` / `isb` / `cjs` / `iopk` — внутренние сервисы операторов,
`arm` / `cabinet` — рабочие места и личные кабинеты.

**Финансовый сектор:** `openapi.mtbank.by`, `openapi.paritetbank.by`, `ibapi.rrb.by`,
`edo.bcse.by` (БВФБ), `secure.bidmart.by`.

**Прочее:** `mdom.by` (`komplat` — коммунальные платежи), `podpis.by`.

⚠ Разбивка сделана по доменным именам. Часть внутренних префиксов (`iopk`, `cjs`, `sks`,
`maxk`) достоверно не расшифровывается — назначение уточнять у самих операторов.

### 2.4. Наличие API

| Система | API | Условия |
| --- | --- | --- |
| **МСИ** | Да, OAuth2 / OIDC | Аутентификация и получение персданных ФЛ через агента по идентификации; после договора выдаётся токен доступа к тестовой среде. Либо прямой договор с НКФО «ЕРИП» |
| **ЕРИП (платежи)** | Да | Протокол взаимодействия для расчётных агентов и производителей ПО, только по договору |
| **Банки** (MTBank, Приорбанк, Альфа) | Да | Заявление → договор → банк выдаёт логин, пароль и техдокументацию. У Приорбанка — портал «Магазин API» после регистрации в Интернет-банке 2.0. Документация непубличная |
| **НБРБ** | Частично | Открытые API есть на справочники и финансово-экономические показатели; у `rvd` / `asoi` публичного API нет — только портал с ЭЦП |
| **Программные кассы** | Да, REST | У операторов (webkassa и другие) — интеграция с учётными системами; готовые интеграции с 1С у ikassa, TitanPOS, WebKassa, «Электронный чек», Light Kassa Bel. К самой СККО напрямую доступа нет — только через оператора |
| **АВЕСТ** | Да, SDK | Тестовые площадки и dev-контуры и есть песочница для встраивания |
| **МНС, ФСЗН, Белстат, Белпочта (`npas`)** | Нет публичного | Порталы с ЭЦП плюс форматы файлов выгрузки. Для МНС — через операторов ЭДО |

### 2.5. Что из этого реально применимо

Для интеграции с внешними системами пригодны три направления: **МСИ** (авторизация
клиента, получение ФИО / УНП / ИН), **банковские Open API** (выписки, платежи) и
**программные кассы** (фискализация). Все три — REST, все три доступны только по
договору, у всех есть тестовый контур.

Остальное — либо порталы без API, либо инфраструктура ЭЦП. Если задача сводится к
подписанию документов на стороне серверного приложения, дешевле идти в **облачную ЭЦП**
(`cloud-ds` / `cloudsign`): она снимает необходимость в AvTunProxy и токенах на клиенте —
закрытый ключ хранится в защищённом облаке, а доступ подтверждается через мобильное
устройство.

⚠ Для нашего шлюза это означает вот что: облачная ЭЦП **не отменяет** потребность в BTLS.
Подпись и транспорт — разные слои: до облачного сервиса подписи ещё нужно доехать, а он
сам живёт за СТБ 34.101.65.

## 3. Развёртывание

Шлюз ставится как один контейнер рядом с приложением. Быстрый старт и полный список
переменных — в `README.md`; здесь то, что в справку по переменным не влезает.

**Куда его включать.** Только во внутреннюю сеть compose, и порт наружу не публиковать.
Шлюз не терминирует свой TLS и никого не аутентифицирует: любой, кто до него дотянулся,
ходит в банк от нашего имени. Единственное, что он держит сам, — список путей в
`nginx.conf.template`, и это граница «какие эндпоинты банка вообще достижимы», а не
«кому можно». В `README.md` § «Граница безопасности» это же сказано с той стороны, с
которой читает оператор.

**Что монтируется.** Связка ГосСУОК — томом в `/etc/crypto-gw/ca`, только на чтение. В
образе намеренно нет `ca-certificates`, поэтому смонтированная связка — весь доверенный
набор, какой у шлюза есть. Побочный эффект полезный: подменить хост назначения на сервер
с честным публичным сертификатом не выйдет, проверка не пройдёт.

**Чем доказывается, что развернулось.** Три гейта внутри `Dockerfile` (криптостек
собрался, движок грузится, nginx слинкован с нужным OpenSSL) плюс два при старте в
`entrypoint.sh` (связка читается, связка проверяет эталонный сертификат банка). Первый
из стартовых — фатальный, второй — предупреждение: он честно краснеет и во время ротации
корней, а отказ стартовать в этот момент был бы аварией, которую мы устроили себе сами
(см. [#4](https://github.com/bx-shef/bee2-tls-gateway/issues/4)).

**Версия образа — по тегу, не `latest`.** Криптостек собирается из исходников по пинам,
и «поехало само» здесь стоит дороже, чем ручное обновление.

## 4. Эксплуатация

**Что попадает в логи.** Формат `gw` намеренно не содержит пути запроса: в пути ездит
номер счёта (`/open-banking/v1.0/accounts/<IBAN>/statements`), а это финансовый
идентификатор, которому нечего делать в агрегации. Вместо пути — `route=`, метка ветки
allowlist: видно, какой эндпоинт отработал, без самого адреса.

По той же причине `error_log` поднят до `crit`, а не `error`: формат `error_log` у nginx
не настраивается, и строки уровня `[error]` несут полную строку запроса — с тем же
номером счёта. Те же отказы уже видны в access-логе как `status=502` с `route=`, только
без идентификатора. Для разбора инцидента уровень поднимают до `info` временно и
возвращают обратно.

**Живой прогон против банка.** В CI его нет и быть не может: нужен боевой хост, доступ
по договору и сеть наружу. Делается руками, и доказательством считается `upstream=` в
логе — код, пришедший от банка, а не выдуманный nginx. Образец такого прогона (401 от
токен-эндпоинта на заведомо неверных кредах) лежит в `README.md` § «Проверено вживую».
Контроль к нему обязателен: `openssl s_client` на тот же хост, который обязан упасть с
`unknown cipher returned` — иначе непонятно, шлюз сработал или хост в тот день отвечал
обычным TLS.

**Одно ядро занято всегда.** `bee2evp_init()` поднимает busy-loop как источник энтропии,
и выключается он только вместе с процессом. Смягчено `nice -n 19` и лимитом CPU; на
burstable-инстансы шлюз не ставится — подробности в
[#8](https://github.com/bx-shef/bee2-tls-gateway/issues/8).

**Остановка.** `STOPSIGNAL SIGQUIT`, потому что у nginx семантика сигналов обратна
привычной: TERM — быстрое выключение с обрывом соединений, QUIT — аккуратное. Без этой
строки рядовое обновление образа резало бы запрос к банку посередине.

### Замена связки ГосСУОК

Самый неприятный отказ шлюза — не громкий, а тихий. Когда корни истекут или банк
перевыпустит цепочку, `proxy_ssl_verify on` начнёт отклонять рукопожатие, и со стороны
потребителя это выглядит **не как авария, а как «банк перестал присылать выписки»**:
никого не разбудит, ничто не покраснеет, расхождение всплывёт через недели на сверке.
Поэтому замена — плановая работа, и заранее.

**Простоя при замене нет, если делать набором.** Связка — это множество якорей доверия:
новый корень кладётся **рядом** со старым, оба живут вместе весь переход, старый убирается
после. Менять «один на другой» одномоментно незачем и рискованно.

Порядок:

1. **Собрать кандидата.** Корни берутся с `nces.by`, и оттуда же берётся риск: подменивший
   ответ подменит корень доверия. Поэтому скачанное **никогда не подставляется
   автоматически** — мы автоматизируем обнаружение изменений, а не доверие им
   (`ca/README.md`, раздел «Ротация»). ⚠ `nces.by` отвечает 503 зарубежному трафику, так
   что этот шаг делается из Беларуси.
2. **Проверить кандидата ДО выката**, тем же механизмом, которым потом будет проверяться
   банк:

   ```bash
   # сроки — стоковым openssl достаточно
   bash scripts/check-ca.sh /путь/к/candidate.pem ca/bank-leaf-reference.pem

   # цепочка — только патченным движком: стоковый openssl не читает ключи bign
   docker run --rm -v /путь/к:/cand:ro --entrypoint /opt/btls/bin/openssl \
     ghcr.io/bx-shef/bee2-tls-gateway:v1 \
     verify -no_check_time -CAfile /cand/candidate.pem /etc/crypto-gw/ca/bank-leaf-reference.pem
   ```

   Кандидат, который **не подтверждает известный сертификат банка, до прода не едет.**
   Связка, где лежит только корень без промежуточного, проходит любую синтаксическую
   проверку и потом 502-ит каждый запрос — ловится это только настоящим `verify`.
3. **Подменить том и перезапустить контейнер.** Связка монтируется томом
   (`./ca:/etc/crypto-gw/ca:ro`), а не берётся из слоя образа, именно чтобы замена не
   требовала пересборки и передеплоя ровно тогда, когда импорт уже стоит.
4. **Убедиться по логу старта**: `проверка цепочки: bundle подтверждает эталонный
   сертификат банка — OK`. Этот гейт намеренно предупреждает, а не падает: во время
   ротации он законно краснеет, и отказ стартовать в этот момент был бы аварией,
   устроенной себе самим.
5. **Убрать старый корень** — отдельным шагом, после того как переход состоялся.

**Что следит за сроками.** Три уровня, намеренно разной громкости:

| когда | что | реакция |
| --- | --- | --- |
| при старте контейнера | `entrypoint.sh`: осталось меньше `GW_CA_WARN_DAYS` (по умолчанию 90) | громкое предупреждение в лог, **старт не блокируется** |
| еженедельно | job `pins`: `scripts/check-ca.sh` по копии в репозитории | заводит issue |
| при каждой сборке | гейт 3 в `Dockerfile` | сборка падает, если связка не подтверждает эталон |

⚠ Ни один из них не падает на истечении корня в проде — и это выбор, а не недосмотр.
Уронить работающий шлюз из-за приближающейся даты значит устроить ровно тот простой,
которого мы избегаем. Громкость нарастает заранее; решение остаётся за человеком.

## 5. Разбор решений

Что пробовали, что сломалось, чем платим. Раздел ведётся с первого технического решения:
запись делается **в том же PR**, где решение принято, пока причина ещё в голове.

- **2026-08-13. nginx уведён с legacy-ветки 1.28 на stable 1.30.4 — и вывод «не наш случай»
  пришлось отменить по дороге.** Пин 1.28.0 нёс **CVE-2026-1642 (SSL upstream injection)**:
  при проксировании на TLS-апстрим атакующий с MITM-позицией со стороны апстрима мог внедрить
  открытый текст в ответ. Это ровно то, чем занят шлюз.

  ⚠ **Разбор ошибки, которая едва не осталась в проекте.** Рядом в перечне лежит
  **CVE-2026-42533** (heap overflow, severity major). Сначала он был назван нашим по
  совпадению названия: «map and regex», а `nginx.conf.template` использует `map` с
  регулярками. Потом — отвергнут как не наш, потому что описание NVD требует
  **capture-групп** в regex, а у нас скобок нет. **Оба вывода были поспешны.** В описании
  два условия, и второе звучит так: «alternatively… using a non-cacheable variable in a
  string expression». А `proxy_pass https://bank$uri$is_args$args` — это оно и есть:
  проверено по исходникам 1.28.3, `$args` и `$is_args` объявлены `NGX_HTTP_VAR_NOCACHEABLE`.
  Там же проверено, что функции-исправления `ngx_http_script_check_length` в ветке 1.28
  **нет вообще**, а в 1.30.4 она стоит в том числе в `ngx_http_proxy_module.c` — то есть
  ровно на нашем пути.

  Урок не в том, что «надо читать описание, а не заголовок» — это было учтено со второго
  раза и всё равно не помогло. Урок в том, что **описание надо дочитывать до конца**:
  условие срабатывания было составным, и слова «alternatively» хватило, чтобы перевернуть
  решение с «остаёмся на ветке» на «уходим». Отсюда же правило проверки: ходить в исходники
  и смотреть, есть ли там функция-исправление, а не верить своему разбору прозы.

  Чем платим за уход на 1.30.x: это смена **минорной** версии на платёжном пути. Гейты
  сборки и смоук доказывают, что образ собрался, слинкован с нашим OpenSSL и стартует, но
  **не** доказывают, что банк по-прежнему отвечает. Живой прогон после такого бампа
  обязателен, и он ручной. Ветка 1.28 при этом не альтернатива: там дыра major-уровня,
  которая не будет закрыта никогда.

  Хеш архива снят самостоятельно и проверен двумя способами: тем же приёмом заново посчитан
  хеш прежнего пина 1.28.0 и совпал с ним (значит способ верный), а сам архив несёт годную
  подпись сопровождающего nginx. Для криптокомпонента брать хеш «откуда-то» — не вариант.

- **2026-08-13. Атрибуция едет внутрь образа, и bee2 — это не тот bee2, который найдётся
  первым.** Apache-2.0 §4 обязывает отдать копию лицензии тому, кто получает артефакт.
  Получает он образ, а не репозиторий, — значит `LICENSE`, `NOTICE` и тексты лицензий
  апстримов лежат в образе, в `/usr/share/licenses/`. Тексты **копируются из тех самых
  деревьев, которые собирались**, а не переписываются в репозиторий руками: переписанная
  копия расходится с апстримом молча и ровно к моменту, когда её придёт читать аудитор.
  Сторожит гейт 4 в `Dockerfile` — проверяет наличие и непустоту, потому что `COPY`
  поймал бы только отсутствующий каталог, а пустой файл проехал бы.

  Заодно выяснилось, чего в задаче не было. Issue [#6](https://github.com/bx-shef/bee2-tls-gateway/issues/6)
  говорит «bee2 / bee2evp распространяется под Apache-2.0», и для bee2evp это правда. Но
  **bee2 бывает двух видов**: подмодуль `bee2` внутри bee2evp указывает на
  `agievich/bee2` (Apache-2.0) — а в той же организации `bcrypto`, что держит bee2evp,
  лежит репозиторий `bcrypto/bee2` под **GPL-3.0**. Проверено выкачиванием файлов лицензий
  из обоих репозиториев, не по памяти — причём имена файлов у них разные: у `agievich/bee2`
  это `LICENSE.txt`, у `bcrypto/bee2` — `LICENSE`, и запрос «того же файла» во втором
  репозитории отдаёт 404. Мелочь, но именно на таких мелочах проверка превращается в
  «вроде посмотрел». Цена ошибки несимметрична: перепутав их, мы бы либо зря
  объявили copyleft на компоненте платёжного пути, либо — хуже — не объявили бы его,
  будь зависимость действительно GPL. Поэтому предупреждение вынесено и в `NOTICE`, и в
  `README.md`: атрибуцию проверяют по имени организации, а имя тут ведёт не туда.

  Правки чужих исходников названы отдельно, этого требует Apache-2.0 §4(b): патч BTLS к
  OpenSSL (авторства bee2evp, мы только применяем) и починка `scripts/source.sh` у
  bee2evp. Сами исходники мы не распространяем — только бинарники.

  Три решения внутри, которые стоит назвать, чтобы их не переигрывали вслепую:

  - **`NOTICE` написан по-английски** — отступление от правила «пользовательский текст
    русский, без исключений». Обосновано тем, что его читатель — не мы: файл уезжает
    внутри образа к любому получателю, включая аудитора и юриста, которые русского могут
    не знать. Корневой `LICENSE` по той же причине английский с первого коммита. Правило
    остаётся в силе для всего остального.
  - **Версии компонентов в `NOTICE` не пишем.** Написанная там «nginx 1.28.0» стала бы
    вторым источником правды рядом с `ARG` в `Dockerfile` и разошлась бы с ним на первом
    же бампе, оставив CI зелёным. Обязательства по лицензиям от версии не зависят, так
    что дешевле убрать повод для расхождения, чем заводить сторожа против него.
  - **У гейтов `Dockerfile` нет мутационного сторожа**, в отличие от проверок конфига.
    Это осознанно: одна мутация стоила бы полной пересборки криптостека (~7 минут), то
    есть проверка «сторож жив» была бы дороже всего остального CI вместе взятого.
    Гейты 1–4 сторожатся только тем, что падение сборки видно сразу. Знать об этой
    разнице важнее, чем закрыть её: нить «инвариант → чем держится» у них тоньше, чем у
    `nginx.conf.template`.

- **2026-08-13. План Б на исчезновение bee2evp: вендорить, а не покупать — пока патч
  прикладывается.** Весь стек висит на одном открытом проекте небольшой группы, и
  компонент стоит на платёжном пути. Что известно на сегодня:

  - **На чём закреплены.** Коммит `2ae3c71e`, выбран после живого прогона против боевого
    банка, а не как «последний на тот момент». Он пинует весь стек разом: `scripts/`
    тянут bee2 подмодулем и клонируют OpenSSL по тегу, так что одна sha фиксирует и
    движок, и bee2, и патч BTLS.
  - **Вендорить можно.** Apache-2.0 прямо разрешает форк и распространение производной
    работы — юридического препятствия держать свою копию нет, нужна лишь сохранённая
    атрибуция, которая теперь и так есть. Технически это копия ~репозитория bee2evp
    вместе с подмодулем и каталогом `btls/patch/`.
  - **Чего это стоит на самом деле.** Не хранения копии, а **сопровождения патча BTLS
    против ветки OpenSSL**. Патч написан под конкретный тег (`btls/patch/<tag>.patch`), и
    как только OpenSSL 3.5 уйдёт с поддержки (2030), кто-то должен перенести его на
    следующую LTS. Это работа на знание внутренностей libssl, и она не автоматизируется.
    Пока апстрим жив — платим ноль; как только исчезнет — платим этим.
  - **Если не потянем — покупка сертифицированного СКЗИ** (АВЕСТ: AvCSP / AvTerminal,
    см. §2). Это возврат к тому, от чего ушли, и он же снимает вопрос признания
    несертифицированной реализации банком.

  ⚠ **Деньги и сроки покупки СКЗИ здесь не названы намеренно: их никто не запрашивал.**
  Ставить в план цифру «по ощущениям» хуже, чем честный пробел, — по ней начнут считать.
  Запросить коммерческое предложение стоит заранее, а не в момент, когда план Б
  понадобится.

- **2026-08-13. Проверки конфига сторожатся мутациями, потому что одна из них была
  мёртвой.** `scripts/check-config.sh` собирал список переменных `envsubst` регуляркой
  `\$\{([A-Z0-9_]+)\}` — только ПРОПИСНЫЕ имена. Проверка № 4 в том же файле следит, чтобы
  в этот список не попала переменная **самого nginx**, а они все строчные (`$status`,
  `$uri`, `$args`): искомое в список не попадало никогда, и покраснеть проверка не могла
  в принципе. Печатала «ok» и была неотличима от работающей.

  Цена промаха измерена запуском, а не прикинута: `envsubst '${status} ${GW_LISTEN}'`
  превращает `status=$status` в `status=` — nginx такой конфиг принимает и стартует, поле
  в логе просто исчезает. То есть поломка молчаливая, и нашлась бы она по пустой колонке в
  агрегации через недели, а не по красному CI.

  Чем платим: появился второй скрипт, `scripts/check-config-mutations.sh`, и он **нарочно
  хрупкий** — тринадцать мутаций правят `nginx.conf.template` и `entrypoint.sh` по
  паттернам, и переформатирование шаблона паттерн ломает. Это выбрано осознанно: «мутация
  не применилась» считается провалом наравне с «проверка не покраснела», иначе сторож
  тихо перестал бы что-либо доказывать — ровно та болезнь, ради лечения которой он и
  написан. Красный CI и поправленный паттерн дешевле.

- **2026-08-13. Правила защиты `main` не хранятся в репозитории.** Сначала ruleset лежал
  файлом `.github/rulesets/main-protection.json` — как воспроизводимый конфиг. После импорта
  файл удалён решением владельца: он не является источником правды (GitHub его не читает),
  а лишний источник правды расходится с настройками молча, и следующий верит файлу. Платим
  тем, что состав правил теперь виден только в Settings → Rules и в кратком пересказе в
  `CLAUDE.md`; при изменении правил пересказ обязан обновляться в том же PR.

- **2026-08-13. Откуда берётся busy-loop и как ту же задачу решил АВЕСТ.** Разбор сделан
  запуском, а не чтением: собран bee2 на том же коммите, что приезжает в образ
  (`d9e689a0`), и установлен AvTunProxy 5.10.12 под Linux.

  **У нас.** `bee2evp_init()` — это один вызов `rngCreate(0, 0)`, никаких потоков он не
  создаёт. Поток появляется глубже: `rngCreate` опрашивает **все** источники подряд
  (`trng, trng2, sys, sys2, timer, jitter`), берёт по 32 байта, хэширует их belt-хэшем и
  засевает `brngCTR` по СТБ 34.101.47.

  ⚠ **Виноват источник `jitter`, а не `timer`** — вопреки тому, как это описано в
  [#8](https://github.com/bx-shef/bee2-tls-gateway/issues/8) и как считалось здесь до
  13.08.2026. Оба живут в `rng_timer.c`, отсюда и путаница, но работают по-разному:

  - `rngTimerRead` (`timer`) считает такты обычным `tmTicks()` и потоков не создаёт;
  - `rngJitterRead` (`jitter`) считает такты `tmCtrTicks()`, а его проверка доступности
    `rngJitterIsAvail()` **сама вызывает** `tmCtrStart()` — и тот поднимает поток-счётчик
    `while (_tm_ctr_loop) _tm_ctr_ticks++`, закрываемый только через `utilOnExit`, то есть
    при выходе процесса.

  Разделено экспериментом, а не чтением: пропуск только `jitter` — `user 0,026 с`, пропуск
  только `timer` — `user 5,010 с`.

  ⚠ **Формулировка дефекта: у проверки доступности вечный побочный эффект.** Функция вида
  `IsAvail` обязана отвечать на вопрос «источник доступен?», а `rngJitterIsAvail()` заодно
  и навсегда запускает поток. Остальные `IsAvail` в файле чистые.

  Усугубляет несогласованность внутри того же файла. Источники читает не только
  `rngCreate` при засеве: `rngStepR` — функция, через которую bee2evp вырабатывает ключи,
  подписи bign и ключи belt-шифров, — подмешивает свежие байты **на каждом вызове**. Но у
  неё есть ранний выход:

  ```c
  // rngStepR: набрали сколько просили — дальше не идём
  while (read < count && pos < COUNT_OF(sources)) { ... }

  // rngCreate: опрашиваются все шесть, всегда
  for (pos = 0; pos < COUNT_OF(sources); ++pos) { ... }
  ```

  Поэтому на машине с исправным `trng` до `jitter` доходит **только** `rngCreate` — и
  оставляет после себя поток, жгущий ядро до конца процесса, хотя энтропии хватило на
  первом же источнике. `rngStepR` в тех же условиях до `jitter` не доходит никогда.

  ⚠ Сказать «счётчик в ключи не попадает» **нельзя**: через `rngStepR` источник `jitter`
  может попасть в выдачу, если предыдущие источники не дали нужного объёма. Верно другое,
  более узкое: привести `rngCreate` к тому же раннему выходу, что уже есть в `rngStepR`.
  Это устранение несогласованности, а не удаление источника энтропии. Здоровье источников
  на конкретной машине показывает пункт 3 в `scripts/check-crypto.sh`, а не догадка.

  **Измерено.** Программа, которая вызывает `rngCreate(0, 0)` и дальше просто спит пять
  секунд: `user 5,089 с` до правки и `user 0,003 с` после. То есть ~96 % ядра уходило в
  поток-счётчик. После правки `st alg`, `st rng` и `es print` проходят.

  **У АВЕСТ.** Устройство другое на всех уровнях. Клиент собран **пропатченным Go**
  (`go1.16.3-av-r46045`) — они форкнули `crypto/tls` и добавили туда belt и bign
  (`av/src/crypto/tls/cipher_suites_by.go`), тогда как мы патчим OpenSSL. Энтропия
  берётся из системы штатным способом (`getrandom(2)`, `/dev/urandom`), при наличии —
  с аппаратного носителя (`TokRandomGenerator`) и от пользователя через внешний callback
  (`CKA_AV_EXT_RANDOM_CALLBACK`); разворачивается всё тем же CTR-генератором на belt
  (`AvcBhfCtrRandomGenerator`, `rng_ctr_belt.go`). Busy-loop нет ни в каком виде.

  ⚠ **Главная находка: у АВЕСТ случайность приезжает по сети.** При старте клиент идёт в
  `http://rand.avtunproxy.by/v1/cms?pubkey=<свой ключ>&size=128` и получает 128 байт в
  структуре CMS (`application/cms`, DER PKCS#7 Signed Data) — то есть подписанных.
  Проверено запросом: сервис отвечает. Это снимает вопрос «где взять энтропию на голой
  машине» ценой зависимости от доступности сервиса и доверия к нему.

  ⚠ И ещё: `avc self-test result: OK` в первых строках лога. Самотестирование при старте —
  ровно то, чего СТБ 34.101.27 требует от СКЗИ как от изделия. У нас такого шага нет.

  **Чем платим, что не патчим сами.** Диагноз точный и место известно, но правка трогает
  сбор энтропии в криптоядре — это ровно тот код, который потом читают два эксперта на
  испытаниях. Свой патч превратил бы нас в форк bee2, который придётся защищать отдельно,
  при том что наше сильное место обратное: мы интегрируем эталонную реализацию. Решение
  прежнее: не патчим, фиксируем разбор и меряем здоровье источников проверкой.

  Для апстрима видны два направления, и выбор между ними — их: либо дать `rngCreate` тот
  же ранний выход, что уже есть у `rngStepR`, либо убрать побочный эффект из
  `rngJitterIsAvail()` — останавливать поток-счётчик после засева. Второе сохраняет
  перемешивание всех источников и снимает постоянную нагрузку, но требует API, которого
  сейчас нет: `tmCtrClose()` статический и вызывается только через `utilOnExit`.

  ⚠ Отправить это в `agievich/bee2` из рабочей сессии не удалось — доступ к чужим
  репозиториям в ней закрыт (`fork_repository`: «Access denied»). Материал подготовлен и
  ждёт отправки; текст и патч — в
  [#8](https://github.com/bx-shef/bee2-tls-gateway/issues/8).
